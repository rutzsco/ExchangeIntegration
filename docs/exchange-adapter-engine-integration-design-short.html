Design document · short version · Draft v0.3 · 2026-11-03

Exchange Adapter ↔ AI Workflow Engine

Built, not yet verified live. This design is built in the adapter as service mode (--run), next to the original connectivity test mode (--probe). Both are covered by automated tests only. Neither has run against the customer's Exchange or Azure yet (see consideration 1).

1Overview

Invoices arrive as emails in an on-premises Exchange mailbox. A small Windows service, the Exchange Adapter, copies each email's attachments to Azure Blob Storage and tells the cloud AI Workflow Engine about it through Azure Service Bus. The Engine checks the invoice and sends back instructions that the adapter carries out in Exchange: email the sender if the invoice is invalid, and move the message to the Processed folder.

Files in storageMessages carry only IDs and a link, so they stay small (256 KB limit on Standard).
The adapter calls outNothing in Azure connects into the customer network: no inbound firewall rules.
Safe to repeatEach email has a stable ID, so a retry is recognized, not duplicated.
No stored secretsWindows identity for Exchange, Entra ID for Azure. No passwords or keys.

One executable has two modes:

  • --probe (test mode) runs one read-only Inbox check and exits. It proves Exchange access and needs no Azure.
  • --run (service mode) runs the two loops below until stopped, normally as a Windows service.

Service mode keeps no database or local state: Blob Storage holds its checkpoints.

2Architecture

3Email in: Exchange → Blob Storage → Service Bus

  1. Read. Every PollIntervalSeconds (60 s by default) the adapter lists the Inbox, oldest first, through Exchange Web Services (EWS), as the Windows service account. It captures at most MaxMessagesPerPoll (20) new emails per pass. The email stays in the Inbox, unchanged. Emails without a Message-ID are left alone and reported in the log.
  2. Save. Each file attachment goes to Blob Storage under <messageKey>/attachments/. Attached emails are counted but not stored. A small manifest.json (sender, subject, file list) is written last, so its presence means the capture is complete.
  3. Announce. One invoice.received message, which only points at the manifest, goes to Service Bus. Only then does the adapter mark the manifest as announced (blob metadata), and that mark is its only checkpoint. After a crash the email is captured and announced again: Service Bus duplicate detection drops the repeat, and the Engine treats a repeat as harmless.
  4. Process. The Engine receives the message, reads the manifest and files from Blob Storage with its own identity, and validates the invoice.

4Decision back: Engine → Service Bus → Exchange

  1. Command. A valid invoice gets a move. An invalid one gets a reply first, and the move only once the reply's result says it worked. If the Engine cannot decide, it sends nothing and an alert is raised.
  2. Act. The adapter pulls one command at a time and checks it against its own rules: this mailbox, a folder from its MoveFolders list, and a commandId and messageKey that belong to the email. It finds the email in the Inbox by Message-ID and carries out the command.
    • A reply is a new plain-text email, sent as the mailbox to the original From address only (never Reply-To) and threaded with In-Reply-To.
    • The adapter refuses to reply to mail from the mailbox itself or automatic mail (Auto-Submitted).
    • A command record in Blob Storage makes repeats safe: work already done is skipped, and a reply is sent at most once.
  3. Report. A succeeded or failed result goes back to the Engine. A failure has a reason, and retryable says whether sending the same command later may work. On a failure the email stays in the Inbox and an alert is raised, so nothing is moved or sent silently. A message that is not a valid command (bad JSON, no usable commandId) goes to the dead-letter queue instead.

5Messages

Three small JSON messages cross Service Bus. They carry IDs and links, never email content.

MessageDirectionKey fields
invoice.receivedAdapter → EnginemessageKey, mailbox, internetMessageId, receivedUtc, link to manifest.json
exchange.command.reply
exchange.command.move		Engine → AdaptercommandId, messageKey, internetMessageId, mailbox, reply.bodyText or move.folder
exchange.command.resultAdapter → EnginecommandId, messageKey, status (succeeded or failed), reason, retryable

messageKey is 32 hex characters of a SHA-256 hash of the mailbox and the email's Message-ID. It names the blob folder, is the Service Bus message ID of invoice.received and starts every commandId (for example <messageKey>.reply), so repeats are recognized. Reusing a commandId returns the first result, so a deliberate second reply needs a new suffix. Results carry commandId as their Service Bus correlation ID.

6Further considerations

Topics for the next iteration. "As built" marks what this version decided; the rest is still open.

#TopicConsideration
1Prove Exchange and Azure accessNothing has run against the customer's Exchange or Azure yet. First, --probe must succeed as the real service account, with Kerberos or NTLM recorded. Then run --run against a test mailbox. Still to confirm live: a new message accepts In-Reply-To and References; lookup by Message-ID; reading the Auto-Submitted header; sending as the mailbox; the folder lookup; and Azure sign-in through Arc.
2Mailbox permissionsAs built: Full Access plus Send As (simplest). Folder-level rights (narrower) or scoped impersonation remain options.
3FoldersAs built: the Engine may only name folders listed in Exchange:MoveFolders (default Processed). These must be top-level folders that already exist; the adapter never creates folders. Open: separate Invalid or Review folders, and nested folders.
4Email to the senderAs built: plain text from the invoice mailbox to the original From address only. There is one reply per commandId, and no reply goes to automatic mail or to the mailbox itself. Open: fixed templates or AI-written text, who approves them, and a cap on replies per sender.
5Untrusted contentEmail text and attachments are untrusted input to an AI system: they must never choose recipients, folders or commands. Scan for malware; the verdict arrives after upload.
6Azure sign-in, networkAs built: DefaultAzureCredential, meaning managed identity through Azure Arc or a certificate, never keys. Azure:UseWebSockets moves Service Bus from TCP 5671 to 443. Open: a proxy; private endpoints need Service Bus Premium.
7Failures, monitoringAs built: failed emails are retried on the next poll, and commands get a retryable flag. Invalid commands are dead-lettered, and Azure outages are left to Service Bus redelivery. A reply whose outcome is unknown is never resent. Open: crash tests on a test system, a standby adapter (today: one adapter per mailbox), and alerts on heartbeat, queue depth, dead letters and oldest Inbox email.
8Volumes, retentionEmails per day, largest attachment and required speed set polling, size limits and throttling headroom. As built, every poll lists the whole Inbox, so moving handled emails keeps it fast. How long are invoices kept, and is a legal hold needed?
9Running as a serviceAs built: --run is registered with sc.exe and logs to the Windows event log. Open: deployment automation, separate dev, test and production resources, a test mailbox, and gMSA.
10Exchange Online laterEWS is being retired in Exchange Online (from 1 Oct 2026); Microsoft says on-premises Exchange Server is not affected. If the mailbox ever moves, Exchange access switches to Microsoft Graph.
